# V0.8.6 Profile Governance

Implementation target: Issue #30 / PH Pilot Roadmap Phase 1.

## Launch profile policy

- Customer remains self-service and private by default.
- Merchant, Supplier and Courier are invite-only.
- Local Services may start an application without an invitation, but the profile remains non-operational until reviewed.
- `profiles.enabled` is no longer sufficient authority for governed roles: an active `profile_authorizations` record is required at the public gateway.

## Territory rule

No Philippines pilot location is hard-coded or invented by this implementation.

The bootstrap Super Admin must create a `territories` record explicitly. Only territories in `onboarding` or `active` state accept invitations/applications.

Invitations, applications and authorizations retain their territory scope.

## Bootstrap administration

Until the scoped RBAC work in Issues #24/#29 is implemented, account 1 is the only governance Admin.

The UI supports:
- creating operating territories;
- inviting Merchant / Supplier / Courier by email;
- reviewing applications and private evidence;
- approving or rejecting;
- approving Local Services categories separately;
- suspending and reactivating profile authorizations with an audit reason.

This bootstrap rule is a temporary migration boundary, not the final Admin authorization model.

## Service Provider category gating

A Service Provider application can request multiple categories.

Only categories selected in the Admin approval become active. A category marked `credential_gate` does not activate unless current verified credential evidence exists. Platform approval must not be displayed as a government licence.

## Suspension invariants

Suspension stops future operational use but does not delete history.

- Merchant storefront is paused.
- Courier availability is disabled.
- accounting, order, incident and audit history remain intact.

## Validation gate

Before merge:

1. GitHub Actions passes on the exact PR head SHA.
2. Railway builds the exact branch head SHA and runs `npm test`.
3. PostgreSQL governance migrations execute successfully.
4. `/health` passes.
5. Runtime chain terminates at `server-profile-governance.js` on the public port.
6. Validation creates no real operating territory, invitation or approval automatically.

No credentials, invitation tokens or private evidence belong in this document.


## Super Admin self-test activation exception

An account with an **active `super_admin` assignment** may activate its own Customer, Merchant, Supplier, Courier or Local Services profile directly from **Account Settings → Manage profiles** for product verification.

This is a narrowly scoped owner-testing exception:

- it bypasses email verification, invitation, onboarding and document gates only for the active Super Admin account itself;
- it does not weaken onboarding or approval rules for ordinary users, delegated Admins, Merchants, Suppliers, Couriers or Service Providers;
- direct activations are forced to private profile visibility;
- the action is written to `profile_governance_events` as `super_admin_self_test_profile_activated`;
- governed-profile authority is explicitly marked with reason `Super Admin self-test bypass`;
- Customer reactivation continues to use the canonical Customer activation path for non-Super-Admin accounts.

The purpose is to let the Project Owner inspect and exercise every profile without creating artificial personal verification evidence or fake compliance documents.
